# CRT Degauss Field (Coherent Strike) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the backlight-on strike read as a degaussing coil instead of a broken video signal. Today `crt_strike_offset` hashes the row index, so adjacent rows are uncorrelated — that is torn hsync or VHS head noise. A degauss field is generated by a coil wrapped around the whole tube: it is large-scale and smooth, so the raster *swims and rocks* as one surface. Same budget, same stages, different law.

**Architecture:** `crt_strike_offset(y, phase)` stops being a hash and becomes a sampled field: a travelling wave along y plus a shear that rocks the frame, both scaled by the existing per-phase amplitude decay and both advanced in phase each frame. The pass already applies the result as a whole-row slide in stage 3 (`sx + row_off`), so nothing downstream changes. The integer sine `crt_wave_q15` already in the file (written for the PCM) is the wave generator — Q16 cycles in, Q15 out, already unit-tested, no new math. The strike's colour side (`ca_boost`) stops being flat per frame and gains the same slow vertical modulation, so purity error moves with the field instead of ringing the whole screen uniformly.

**Tech Stack:** same as always — Pebble C SDK, Unity host suite in `test/test_watchface.c` (includes `../src/c/crt.c` directly), `make test` = format + JS + C, `make visual-baseline`/`visual-check` = emery emulator pixel gate.

**Spec:** the physics review in the CRT design thread — "row jitter is per-row white noise; a degauss field is spatially coherent, so the raster warps and swims as a whole. Incoherent per-row offsets read as VHS head noise or lost hsync. This is the largest deviation and the cheapest to correct." Sound coherence is Task 3.

## Global Constraints

- **Per-row only.** The field is evaluated once per row, never per pixel. Stage 1/2/3 per-pixel cost must not change.
- **No vertical displacement.** A real field also moves the raster vertically, but stage 3 samples `row_ca`, a single-row buffer, and the vertical CA ring holds three rows. Reading a different source *row* is architecturally out of reach and is not in this plan. The shear below is what buys the 2D feel. Do not re-propose per-row vertical offsets without redesigning the row pipeline.
- **Geometry only, no gain.** The strike shakes the raster; it does not dim it. The vignette stays idle-only, as today.
- **Integer math**, `crt.c`'s dense why-with-arithmetic comment register.
- **Determinism per (y, phase)** is retained — the tests depend on being able to recompute an expected offset.
- `crt_strike_offset` keeps its signature and its `flash_phase < 0 || >= CRT_FLASH_PHASES → 0` contract.
- VCS: jj repo. Implementers and reviewers run NO jj mutations and NO git. Work stays in the working tree; per-task test gates stand in for commits.

## The field

Two terms, both driven by the same frame phase θ so they move together:

```
A     = s_strike_amp_px[phase]                       // px, decaying
theta = (uint32_t)phase * CRT_DEGAUSS_DTHETA         // Q16 cycles, per frame
swim  = (A * crt_wave_q15((uint32_t)y * CRT_DEGAUSS_KY + theta)) >> 15
rock  = (A * crt_wave_q15(theta + 16384)) >> 15      // quarter-cycle out of step
row_off = swim + (rock * (2*y - (h-1))) / (2*(h-1))
```

`swim` is the field's spatial ripple travelling down the screen. `rock` is a shear — the frame tilts, which at these amplitudes reads as the whole raster rotating, and rotation is what a real coil does that a pure vertical ripple does not. Quarter-cycle offset so the two peak at different moments and the motion never collapses into one axis.

Constants (all new, in `crt.h`):

| name | value | why |
| --- | --- | --- |
| `CRT_DEGAUSS_KY` | 512 | `y << 9`; 228 rows × 512 = 1.78 cycles down the screen — a smooth double bow, not a ripple |
| `CRT_DEGAUSS_DTHETA` | 24000 | 0.366 cycles/frame, 2.93 over the strike. Avoid 16384 (quarter) and 32768 (flip) — those beat into a static or flickering pattern |

`s_strike_amp_px` is retuned to `{4, 4, 3, 3, 2, 2, 1, 1}`. Peak displacement is `1.5*A` (swim + half the shear), so 6 px at phase 0 — the same worst-case slide as today's table, redistributed. `ca_boost = (A + 1) / 2` then yields `{2,2,2,2,1,1,1,1}` against today's `{3,3,2,2,1,1,1,1}`, which is the intended softening: the fringe no longer has to carry the whole effect now that the geometry moves coherently.

Smoothness falls out of the numbers, and is the property to pin: `d(swim)/dy ≈ A · 2π · 512/65536 = 0.049·A`, so 0.2 px per row at A=4, and the shear adds `2·A/454 ≈ 0.018`. Adjacent rows can differ by 1 px after rounding, never by 2. Today's hash jumps up to `2·A = 12`.

## Purity modulation

`ca_boost` is flat across the screen today, so the strike's channel splay swells uniformly — every pixel fringes harder at once. Real purity error during a degauss is patchy: soft coloured regions that drift. Cheapest honest approximation, evaluated once per row next to the field:

```
boost_row = ca_boost ? ca_boost + (crt_wave_q15((uint32_t)y * CRT_DEGAUSS_KY_P
                                                + theta + 21845) > 0 ? 1 : 0)
                     : 0;
```

The `ca_boost ?` guard is not cosmetic. `ca_boost` is 0 whenever the strike is idle, which is every frame the watch draws except eight per backlight-on — without the guard this plan would add a `crt_wave_q15` call per row to every minute tick forever, to compute a zero. `crt_strike_offset` already early-returns on `CRT_FLASH_IDLE`, so the field itself is strike-only by construction; keep it that way.

`CRT_DEGAUSS_KY_P = 320` (1.1 cycles down the screen) — deliberately not `CRT_DEGAUSS_KY`, so the colour band and the geometry ripple drift against each other instead of locking into one visible stripe. The third-cycle phase offset keeps the band from starting aligned with the swim's zero crossing.

`boost_row` must stay **whole pixels** — stage 1 multiplies it by 3 into the thirds ladder (`q = t3 + (left ? -1 : 1) + 3 * ca_boost`), and `test_crt_strike_should_stack_ca_boost_in_whole_pixels` pins exactly that.

> The reasoning below is kept because the arithmetic is still correct and still
> applies if the firmware fix lands first and a long hum becomes affordable.

The visual runs 8 × 90 ms = 720 ms; the PCM is 320 ms. The hum *is* the field — when the coil stops, the swim stops — so a strike that keeps moving for 400 ms after silence is incoherent. Sizes, against `SPEAKER_MAX_SAMPLE_BYTES_TOTAL = 16384`:

| rate | max duration in budget | 700 ms costs | notes |
| --- | --- | --- | --- |
| 16 kHz | 512 ms | 22,400 B — over budget | cannot reach 720 ms |
| 8 kHz | 1024 ms | 11,200 B | fits; +960 B of `.bss` over today |

So the sample moves to 8 kHz and 700 ms. The mixer runs at 16 kHz and resamples with nearest-index and no interpolation (`track_player.c`), but every component of this sound is under ~500 Hz, so the images land above 7.5 kHz where neither the speaker nor the ear will find them. Watch the `.bss` growth: the buffer is static and the app image has a 64 KB `virtual_size` ceiling.

### What the current sample measures

Generated from the real `crt_strike_synth` and analysed (buffer verified byte-identical against the C):

| property | measured |
| --- | --- |
| envelope | 64 ms linear attack, 64 ms hold, 188 ms linear decay, 4 ms silence |
| pitch | 90 → 55 Hz glide, confirmed by zero crossings |
| harmonics | H2 −5.8 dB, H3 −10.9 dB, nothing meaningful above H3 |
| peak | 27999 (85% FS), zero clipped samples |
| worst sample step | 1161 — no clicks; DC offset 7.9, negligible |
| **energy below 300 Hz** | **100.00%** |
| **energy below 100 Hz** | **75.8%** |

Mechanically the sample is clean. The problem is the band: the highest partial the synth can produce is the 3rd harmonic of the 90 Hz start, i.e. 270 Hz, so *the entire signal* sits under 300 Hz and three quarters of it under 100 Hz. That is exactly where a watch micro-speaker rolls off. The comment claiming the audible weight rides the harmonics does not hold — the harmonics are down there too, at 110-270 Hz falling to 120-180 Hz. And the glide walks what little is audible further *down* as it goes.

### Content changes, all inside `crt_strike_synth`

- **Constant pitch, not a glide.** Magnetostriction sings at twice mains, so the hum sits at 100-120 Hz and stays there while the amplitude decays. Use 110 Hz.
- **Add a rattle partial.** A real degauss is not just the hum; the coil and chassis buzz, and that component is broadband and much higher. Voice becomes 110/220/330/440 Hz at weights 3:2:2:1, which puts ~50% of the energy above 200 Hz and ~28% above 300 Hz, against 0% today. Give the 440 Hz partial a faster decay than the rest so it reads as a transient rattle rather than a tone.
- **Fast attack.** The coil energises instantly. 64 ms of fade-in blunts the one transient the effect has; 8 ms is enough to avoid a click.
- **Exponential decay**, not linear: `env -= env >> k` matches a thermistor and stops the tail sounding like a fader.
- Keep the peak near 28000 — there is headroom to 32767, but the clamp in `crt_wave_q15` exists for a reason and the extra 1.5 dB is not worth approaching it.

## Useful exact values

- `crt_wave_q15(p)`: p is Q16 *cycles*, returns Q15 signed, and it is **cosine-phased, starting at its trough** — read the shape off the code before assuming a sine: `p = 0 → -32767`, `16384 → ~0 rising`, `32768 → +32767`, `49152 → ~0 falling`, period 65536.
- That phasing is wanted here: at θ=0 the top row starts at full displacement, which is what an instantly-energised coil does. It also means the first strike frame jumps away from the idle geometry rather than easing into it.
- h = 228, so `2*y - (h-1)` runs -227 … +227 and the shear divisor `2*(h-1)` is 454.
- θ per phase: 0, 24000, 48000, 72000, 96000, 120000, 144000, 168000 (Q16; values past 65536 wrap by design, that is the cycle).
- `y * 512` at y=227 is 116,224 — nowhere near a `uint32_t` overflow; the only wrap is the intended mod-65536 one.

## Self-Review

**Physics coverage:** coherent large-scale field ✓ (swim + shear, both smooth in y); decay direction ✓ (max at switch-on, thermistor); duration ~700 ms ✓ (real degauss is roughly 1 s); patchy purity error ✓ (row-modulated boost); sound at twice mains with constant pitch ✓. Not modelled and deliberately so: vertical displacement (single-row pipeline), true rotation (shear stands in), field-induced convergence *direction* changes (the boost only grows the existing radial splay).

**Cost:** see Performance below. Per-pixel work is untouched, and idle frames are untouched.

## Performance

Not profiled on hardware — the argument here is the iteration ratio, which holds whatever the clock turns out to be.

Per **row**, during a strike, the field replaces a hash with two `crt_wave_q15` calls, two multiplies and one divide, and the purity band adds a third wave call. Call it +40-50 cycles per row net. Net, because the old hash ends in `noise % (2*amp+1)` — a runtime-operand `UDIV` — and that goes away. `crt_wave_q15` itself is the expensive piece at roughly 15-20 cycles: it does a 32x32→64 multiply and then a 64x32, which on a 32-bit core is a short instruction sequence rather than one op.

Per **pixel**, nothing changes. That is the whole point of keeping the field per-row: 228 row iterations against 45,600 pixel iterations is a 200:1 ratio, and the three per-pixel loops (weighted CA taps, vignette dither, curvature resample) are tens of cycles each. The added work lands somewhere around 10k cycles against a few million — a fraction of a percent of a strike frame. Even if the per-pixel estimate is off by 3x it stays near 1%.

Per **frame budget**, the constraint is unchanged: 8 frames at 90 ms, and the pass has to finish inside a tick or the chain slips. This plan does not move that needle in either direction. If strike frames are already slipping, they were slipping before.

**Idle frames cost nothing new.** `crt_strike_offset` early-returns on `CRT_FLASH_IDLE` and `boost_row` is guarded on `ca_boost`. Every minute tick — which is essentially all of the watch's life — runs exactly the code it runs today. That matters more for battery than anything else in this plan.

**Boundary, worth stating so it is not crossed later:** the field is affordable *because* it is per-row. Evaluating `crt_wave_q15` per pixel to get horizontal field variation would be ~900k cycles a frame — milliseconds, not microseconds. If horizontal variation is ever wanted, it needs a per-row LUT, not per-pixel evaluation.

**RAM, not CPU, is where Task 3 spends.** The PCM buffer goes from 10,240 to 11,200 bytes of static `.bss` (+960 B), against the app image's 64 KB `virtual_size` ceiling — check the `pebble build` memory report, do not assume the headroom.

**Synthesis** runs once, on first strike, inside `crt_backlight_handler` and before `speaker_play_tracks`, so its cost delays the first woomp by its own duration. Today that is roughly 5,120 samples of three wave calls plus two or three runtime divides each. The new voice adds a fourth partial but the exponential envelope removes the per-sample divides, so it should come out close to a wash — and it happens once per app launch.

**Test surface:** one rewritten test (`..._should_jitter_rows_and_decay` — the name should lose "jitter"), one adjusted (`..._stack_ca_boost_in_whole_pixels`), one adjusted (`..._swell_fall_and_never_click`), four new. The coherence pin is the important one: it is the property that distinguishes a field from noise, and it is what a future "make it shakier" change would break.

**Known intentional appearance change:** the strike no longer strobes as noise; it moves. On a 90 ms frame the eye will read discrete steps rather than continuous motion — 11 fps is the ceiling the sound pipeline and the pass leave. If the stepping reads badly on hardware, the dial is `CRT_DEGAUSS_DTHETA` (smaller = less travel per frame = less strobing, at the cost of looking slower), not the frame rate.
